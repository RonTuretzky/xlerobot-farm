01 / Match software to the revised build

Bottle watering and one movable light sensor

The robot waters plants by picking up a small pouring bottle, aiming, tilting briefly and returning it upright. Refill is manual. The electric pump, separate reservoir, hoses, barbs, pump supply, pump diode/fuse and reservoir float are out of V0 scope. Water temperature monitoring and leak pads are deferred. This changes the design, not the Amazon cart.

Keep the ESP32, SEN-13637 moisture probe and ONE BH1750 light sensor. One relay channel briefly powers the moisture probe; no relay actuates watering. Air temperature/humidity remains optional context. Use the robot's existing cameras and one task tool at a time per gripper.

Light-sampling adapter

Extend the removable light paddle to a repeatable canopy-height pose, face upward, check for arm shadows and wait for motion to settle. At default BH1750 high-resolution timing, discard the in-motion reading, wait a complete conversion (up to 180 ms) and collect ten distinct readings over roughly two seconds. Respect actual configured conversion timing; do not reread one cached value. Log median, spread, pose, height, time, saturation, bus errors and validity. Reacquire or flag UNSTABLE if the view/pose/reading is unsuitable; do not move until a desired value appears. Stable is not necessarily accurate: validate the installed sensor against a reference if needed. Lux is not PPFD.

02 / An explicit state machine

Each transition needs evidence and a timeout

*Handling states apply when moving a pod. For in-place inspection, record them as not applicable under the configured workflow; never silently skip a required state. “Care” initially means supervised robot-held bottle watering. Validate manual teleoperation before collecting task demonstrations. Robot wheels stay parked; the arm still moves. The feedback’s weighing, dosing and verification branch becomes available only in an explicitly commissioned dosing profile.

Configure a deadline and explicit expected evidence for every transition. Timeout moves the cycle to PAUSED / NEEDS REVIEW, retaining its last verified state and estimated pod location. Commission safe stop behaviour for each holding state with dummy pods.

03 / Six feedback changes made concrete

Persist what was intended, attempted and verified

1

Durable action records

Assign cycle IDs and command IDs. Save INTENDED before dispatch, ATTEMPTED before a possible physical effect, and VERIFIED only with outcome evidence. Duplicate IDs return the existing result. After a crash in the uncertain interval, mark UNKNOWN and reconcile before continuing. IDs alone cannot guarantee exactly-once physical watering.

2

One shared evidence format

Store pod ID, crop/recipe version, cycle and command IDs, timestamps, sensor values and units, validity/freshness, calibration IDs, original images, intended/attempted/verified states, outcome evidence, interventions, and software/model/policy versions. Keep records locally in SQLite and image files linked by stable identifiers.

Export one incident bundle that explains why care was requested and what was proved. Delivery status must distinguish measured, human-attested, unknown and not attempted. A post-care wetness change never becomes a fabricated volume measurement.

3

Sensor validity is an action prerequisite

Define per-sensor freshness limits, valid ranges, calibration expiry and quality flags in versioned configuration. Reject stale images, wrong pod identity, unconfirmed probe contact and, if enabled, unstable mass. A leak or uncertain grip blocks the relevant action locally, regardless of cloud availability.

4

A small remote exception viewer

Show the current image, evidence age, pod/location, current attempted action, last verified state and reason for the stop. Offer only eligible actions: reacquire evidence, pause, confirm a physically inspected state, or request caretaker service. Disable “retry watering” when delivery is uncertain. Record reviewer identity, reasoning and time; no terminal should be needed for a defined recovery.

5

Fault episodes become regression cases

Simulate every state interruption before travel, then save actual failures with their recovery. Replay duplicates, stale sensors, wrong pods, missing contact, uncertain grip, visible spills, unobservable spill zones, lost acknowledgements, cloud loss and interrupted handling. Use the same event schema in simulation and hardware, clearly labelling which produced each episode.

The sixth feedback requirement—the explicit care state machine—is the foundation above. Recovery and evidence collection ship with the first complete loop.

Camera feature / bottle revision

Visible-spill checks and upright recovery

Proposed software, not implemented protection. Use the existing head/wrist cameras to inspect bottle, nozzle, target pod and catch tray before, during and after a pour. A dark, hidden, stale or out-of-frame spill zone is UNKNOWN, not CLEAR. Dedicated leak pads remain deferred.

  1. Before pouring, require a verified grip, intended pod, visible pour zone, known small starting bottle fill and a tested path back upright. Keep the base parked.
  2. On SPILL, unknown coverage, excessive tilt duration or communication trouble, abort the dose and execute the commissioned return-upright motion if control is available. Do not blindly release or de-energize a tilted bottle.
  3. Total power loss may leave the bottle tilted. Software cannot guarantee it stops draining. Limit fill and use physical containment; test this before considering unattended care.
  4. Record intended/attempted/verified state with unique action IDs. A tilt command is not measured delivery. Unknown pouring never triggers an automatic repeat.
  5. Evaluate labelled visible spills, tiny clear-water spills, glare, arm occlusion, camera failure, empty/full bottle variation and lost acknowledgements. Track false clearances and detection/recovery latency. Stay supervised until relevant gates pass.
05 / Where Jev and Astra fit

Classification is separate from permission

Jev starts in shadow mode: record its recommendation while rules and supervised care remain in charge. Route into normal, needs reinspection, handling fault, watering discrepancy, crop concern, unknown. Conflicting or unfamiliar evidence must allow abstention.

Astra investigates the incident history and proposes reinspection, experiments or bounded policy changes. The local controller checks permission, limits and physical prerequisites. Neither model can override a leak, stale measurement or uncertain grip. Cloud loss must preserve local stop behaviour and any already validated local operations.

The existing helper’s 0.85 heuristic is not a validated farm threshold. The helper is described by the redline; its source has not been independently audited here.

How to measure whether the models help

Compare rules and Jev using exactly the same evidence. Track missed faults, false clearances, unnecessary alerts, remote review minutes, latency and cost. Keep real and simulated episodes separate; independently label outcomes and reserve held-out episodes that were not used for tuning.

The redline’s proposed 120 labelled episodes and at least 10 per priority fault class are an initial collection target, not a reliability guarantee. Keep control authority off until an explicitly reviewed evaluation and a bounded supervised trial pass.

06 / A V0 incident

P07 appears dry, but did the probe touch the sheet?

  1. Identify and inspect: confirm P07, its recipe and a fresh view of the seed-free measuring patch.
  2. Measure: a low reading with unconfirmed contact is INVALID. Save the evidence and pause the watering decision.
  3. Review: Jev records “needs reinspection” in shadow mode. The viewer offers a fresh supervised approach or caretaker inspection.
  4. Care: after valid dry readings and local checks, request supervised watering. Record the human action and any reported amount as human-attested.
  5. Verify: record fresh local wetness and visible-spill status (CLEAR / SPILL / UNKNOWN with coverage evidence). Do not claim independently measured volume. Confirm pod position before completing.
  6. Recover: if a crash leaves watering uncertain, reopen the incident with UNKNOWN delivery. Reconcile with physical evidence and the caretaker; do not automatically request another dose.
07 / Release discipline

Keep the parked loop dependable

Every release must pass accumulated fault regressions, including cloud loss and interrupted handling. A feature that changes contact, motion or watering requires the relevant physical tests again. Record observed outcomes and unresolved cases instead of declaring success from simulation alone.

Initially Astra produces reviewable proposals. Version code, model, calibration and policy changes; retain a working rollback and restore procedure. Keep crop recipes fixed within comparisons unless necessary care requires a recorded deviation.

Defer: autonomous code modification, automatic retraining, complex multi-agent orchestration, mobile navigation, printer pickup and construction demonstrations until the parked care loop is dependable.
